1. Project Overview & Problem Statement

1.1 What ProxiCheck Does

ProxiCheck is a hardware-free, browser-native university attendance management platform. It enables lecturers to initiate cryptographically verified roll-call geofences centered around lecture rooms and allows registered students to record attendance within seconds directly through standard desktop, tablet, or mobile web browsers.

1.2 The Problem It Solves

Traditional university roll call and attendance recording methods suffer from critical structural weaknesses:

  • Paper Attendance Sheets: Heavily prone to proxy sign-ins (students signing on behalf of absent friends), illegible handwriting, damaged sheets, and significant class disruption while passing papers across large lecture halls.
  • Dedicated Biometric Terminals: Fingerprint and facial terminals are cost-prohibitive to install across every classroom, experience frequent hardware breakdowns, and cause massive queues at hall entrances.
  • Static QR Code Systems: Severely compromised because students in the lecture hall snap screenshots of projected QR codes and send them across WhatsApp or Telegram groups for absent students to scan from their rooms.
  • Native Mobile Apps & Beacons: Compelling students to download 80MB+ native mobile application store packages creates compatibility and phone storage barriers, while Bluetooth beacon radio signals unpredictably leak through concrete walls into external hallways.

ProxiCheck eliminates both physical hardware and mobile app installations by utilizing browser geolocation, server-side geospatial verification, single-device fingerprint binding, and institutional email validation.

2. Attendance Process & Verification Mechanics

2.1 Step-by-Step Attendance Workflow

  1. Session Initiation: The lecturer logs into the Faculty Command Center, selects a course, chooses a registered classroom venue (e.g., Step B), sets an allowed radius (10m to 500m), and designates a duration (30 to 120 minutes).
  2. Dynamic GPS Anchoring: The session automatically anchors to the calibrated coordinates of the venue, or dynamically anchors to the lecturer's live device coordinates if the lecture was relocated.
  3. Session Discovery: The active session immediately displays on the student dashboard for all students officially registered in that course.
  4. Presence Submission: The student taps "Check In". The browser requests high-precision satellite coordinates via the HTML5 Geolocation interface.
  5. Multi-Layer Verification: The server verifies device integrity, rejects coarse network signals, computes the geodesic distance to the hall center, and commits an atomic database transaction.
  6. Live Feedback & Audit: The student receives instantaneous confirmation with distance and timestamp, while the lecturer's live attendee radar updates in real time with the student's matric number and check-in time.

2.2 Presence Verification Logic

The verification pipeline validates four sequential criteria without requiring manual calculations:

  • Single-Device Integrity: The student's account must match the physical device hardware fingerprint bound upon registration. This ensures a student physically in class cannot log in on behalf of an absent friend.
  • Sensor Accuracy Filtering: The device's reported GPS horizontal accuracy radius must be within acceptable thresholds (under 50 meters), filtering out inaccurate cell-tower or Wi-Fi triangulations.
  • Geodesic Distance Verification: The server computes the true shortest surface distance between the student's coordinates and the lecture hall center using the Great-Circle navigation algorithm. The student must physically be within the lecturer's configured perimeter.
  • Atomic Concurrency Lock: A composite unique database constraint on session ID and student ID guarantees that duplicate check-ins are blocked atomically.

4. Features: Implemented vs. In-Progress

4.1 Implemented Features

  • Browser-Native Geofencing: Zero app store downloads; students check in directly via browser geolocation.
  • Single-Device Hardware Binding: Enforces 1 device per student matriculation number to prevent proxy logins.
  • Faculty Verification Keys: Pre-provisioned departmental authorization keys prevent student spoofing of lecturer roles.
  • Institutional Email Governance: Strict regex validation requiring students to use OAU student emails and staff to use faculty emails.
  • Venue & Course Management: Full administrative management for lecture theatres and departmental allocations.
  • Live Attendance Radar & CSV Export: Real-time polling monitor and one-click formatted CSV sheet export for academic portals.
  • Individual Course Enrollment: Students can only access roll calls for courses they are officially registered for.

4.2 Exam Eligibility & At-Risk Predictor Feature

To enforce academic regulations requiring at least 75% lecture attendance to qualify for semester examinations, ProxiCheck includes an attendance forecasting engine:

  • Dynamic Attendance Projection: Calculates the student's maximum attainable attendance percentage by summing attended classes with all remaining scheduled classes, divided by total syllabus lectures.
  • Automated Risk Badging: Automatically categorizes students as Safe (≥ 75%), At Risk (60% to 74% with targeted attendance targets), or Barred (< 60% or mathematically unable to reach 75%).
  • Official Examination Docket: Provides lecturers and examination officers with a one-click summary of barred students for faculty board review.

5. System Architecture & Database Design

ProxiCheck employs a 3-tier cloud architecture separating presentation, business logic, and relational persistence:

  • Presentation Tier: Responsive Next.js 15 client handling location capture, active roll-call displays, and real-time radar monitors.
  • Application Tier: Serverless Edge route handlers validating JWT session cookies, running geospatial checks, and managing session lifecycles.
  • Data Tier: Supabase PostgreSQL relational schema enforcing unique constraints, foreign keys, and Row-Level Security policies.

Database Schema Entities

  • profiles: Stores user identity, university email, role (student/lecturer/admin), matric number, and bound device fingerprint.
  • classrooms: Physical campus venues with latitude, longitude, and default radius.
  • courses: Academic courses with departmental code and course title.
  • course_enrollments: Junction table linking students to registered courses.
  • attendance_sessions: Active or historical roll calls with geofence center, radius, and duration windows.
  • attendance_records: Verified check-ins storing session ID, student ID, matric number, recorded distance, and submission timestamp.

6. Development Process & Major Challenges

6.1 Engineering Heritage & Pivot

The project originally began as an ESP32 microcontroller Bluetooth Low Energy (BLE) beacon prototype paired with an Expo React Native mobile application. Field testing revealed critical drawbacks: BLE signal strength through thick university walls was erratic (causing students in outside corridors to register false check-ins), and distributing native mobile applications caused installation friction across different operating systems. The team pivoted to a browser-based geospatial architecture, eliminating hardware dependencies while hardening web security.

6.2 Key Challenges & Solutions

  • Indoor GPS Signal Distortion: Concrete auditoriums can degrade satellite accuracy. Solved by implementing an adaptive sensor accuracy filter and a Live Location Override enabling lecturers to anchor the geofence from their active podium position.
  • Buddy Check-in Prevention: Students sharing login credentials with friends in class. Solved by binding user accounts to a unique browser hardware device fingerprint upon registration.
  • Database Schema Desynchronization: Cloud migrations missing columns during initial account creation. Solved by implementing resilient fallback upsert patterns that guarantee profile persistence before session initialization.

7.2 System Limitations

  • Browser Permissions: Location permission is required by the browser; users who deny permission cannot record presence.
  • Basement Laboratories: Underground halls without satellite line-of-sight require lecturers to expand radius presets.
